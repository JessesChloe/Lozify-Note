## 技术决策记录

### ADR-009: Markdown 标记存储 vs 富文本对象存储

**背景：**
- 富文本应用通常面临两种存储策略：
  1. 存储带标记的原始文本（如 Markdown）
  2. 存储结构化富文本对象（如 Quill Delta、Prosemirror JSON）

**决策：**
- **选择：** 存储 Markdown 风格的原始文本
- **标记语法：**
  - 粗体：`**text**`
  - 下划线：`__text__`
  - 高亮：`==text==`
  - 复选框：`- [ ]` / `- [x]`
  - 标签：`#tagname`

**理由：**
1. **可读性**：数据库中的文本保持人类可读
2. **可移植性**：纯文本格式易于导出/导入
3. **简单性**：无需复杂的序列化/反序列化
4. **兼容性**：未来可轻松迁移到标准 Markdown
5. **调试友好**：直接在数据库工具中查看内容

**替代方案（已拒绝）：**
1. **HTML 存储** → 膨胀严重（`<b>text</b>` vs `**text**`）
2. **JSON 对象** → 需要版本管理，迁移复杂
3. **Android SpannableString 序列化** → 平台绑定，无法跨平台

**后果：**
- ✅ 数据库迁移友好（纯文本字段）
- ✅ 全文搜索可直接工作（无需特殊处理）
- ⚠️ 解析开销在渲染时（可接受，因为有 `remember` 缓存）

---

### ADR-010: 解析顺序策略

**背景：**
- 多种格式标记可能产生冲突（例如：`**==bold + highlight==**`）
- 正则表达式匹配顺序影响最终渲染效果

**决策：**
- **固定解析顺序：**
  1. Checkboxes（先替换为 Unicode 符号）
  2. Bold
  3. Underline
  4. Highlight
  5. Tags
  6. Checkbox 符号着色

**理由：**
1. **Checkbox 优先**：避免 `[ ]` 被误解析为其他格式
2. **从小到大**：先处理短标记（2 字符），再处理长标记
3. **Tag 后置**：#tag 不应被包裹在其他格式中
4. **着色最后**：确保所有结构解析完成后再应用颜色

**示例：**
```kotlin
// 输入：**这是 ==高亮粗体== 文本** 和 #标签
// 解析后：
// - "这是" → Bold
// - "高亮粗体" → Bold + Highlight (两层 SpanStyle 叠加)
// - "文本" → Bold
// - "#标签" → Blue color
```

## 学习与反思

### 1. AnnotatedString 多层 SpanStyle 叠加机制

**关键知识点：**
- `AnnotatedString.Builder` 允许对同一文本范围多次调用 `addStyle()`
- 后添加的 SpanStyle 不会覆盖前面的，而是叠加
- 最终渲染时，Compose 会合并所有应用的 SpanStyle

**实践案例：**
```kotlin
// 同时应用粗体和高亮
addStyle(SpanStyle(fontWeight = FontWeight.Bold), start = 0, end = 4)
addStyle(SpanStyle(background = HighlightYellow), start = 0, end = 4)

// 渲染结果：文本既是粗体，又有黄色背景
```

**经验教训：**
- ✅ 无需担心样式冲突，Compose 会智能合并
- ✅ 解析顺序影响性能，但不影响正确性
- ⚠️ 注意 `start`/`end` 索引必须在范围内，否则抛出异常

---

### 2. TextFieldValue vs String 的选择

**String 的局限：**
- 无法跟踪光标位置
- 无法获取选区范围
- 格式化操作只能追加到末尾

**TextFieldValue 的优势：**
- 包含 `text: String` 和 `selection: TextRange`
- 可精确控制光标位置
- 支持选区操作（选中文本后格式化）

**迁移成本：**
- 需要将所有 `noteContent` 替换为 `textFieldValue.text`
- 需要更新 `TextField` 的 `value` 和 `onValueChange` 参数

**经验教训：**
- ✅ 对于需要精确光标控制的场景，优先使用 `TextFieldValue`
- ⚠️ `TextFieldValue` 是 `@Stable` 类，`remember` 时需正确处理初始化

---

### 3. 正则表达式非贪婪匹配

**贪婪匹配问题：**
```kotlin
// 错误：贪婪匹配 .+ 会匹配到最后一个 **
val pattern = Regex("""\*\*(.+)\*\*""")

// 输入："这是 **粗体1** 和 **粗体2** 的示例"
// 匹配结果：整个 "粗体1** 和 **粗体2" 被匹配（跨越了中间的文本）
```

**非贪婪匹配解决方案：**
```kotlin
// 正确：非贪婪匹配 .+? 只匹配最近的闭合标记
val pattern = Regex("""\*\*(.+?)\*\*""")

// 匹配结果：分别匹配 "粗体1" 和 "粗体2"
```

**经验教训：**
- ✅ Markdown 标记解析必须使用非贪婪量词（`+?`, `*?`）
- ✅ 使用 `findAll()` 而非 `find()`，确保捕获所有匹配项

---

### 4. Compose remember 缓存策略

**问题场景：**
- `NoteCard` 在 `LazyColumn` 中复用
- 如果 `content` 未变化，不应重新解析

**解决方案：**
```kotlin
val annotatedContent = remember(content) {
    RichTextUtils.buildAnnotatedStringWithFormatting(content)
}
```

**remember(key) 行为：**
- `key` 未变化 → 返回缓存值
- `key` 变化 → 重新执行 lambda

**性能优化：**
- ✅ 避免每次 recompose 都执行正则解析
- ✅ 适用于数据驱动的 UI（content 作为 key）
