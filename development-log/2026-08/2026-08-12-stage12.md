## 🐛 踩过的坑（重要！）

### 坑 #1: KSP Internal Compiler Error - 类型不匹配导致缓存崩溃

**现象**:
```
java.lang.IllegalStateException: Storage for [id-to-file.tab] is already registered
```

**根本原因**:
修改 `NoteDao.kt` 的方法签名时，将 `updatedAt` 参数类型从 `Long` 改为 `Instant`，但：
1. **忘记添加 `import java.time.Instant`**
2. 调用处 `NoteRepositoryImpl.kt` 仍在传入 `Instant.now().toEpochMilli()` (Long 类型)

**错误的修改过程**:
```kotlin
// ❌ 第一次尝试（错误）
val now = System.currentTimeMillis()  // Long
noteDao.updateArchiveStatus(noteId, true, now)  // DAO 需要 Instant！

// ❌ 第二次尝试（类型推断失败）
val now = Instant.now().toEpochMilli()  // 显式 Long
noteDao.updateArchiveStatus(noteId, true, now)  // 还是类型不匹配
```

**正确的修复方案**:
```kotlin
// ✅ 最终正确方案
// 1. NoteDao.kt 添加导包
import java.time.Instant

// 2. DAO 方法签名明确为 Instant
suspend fun updateArchiveStatus(noteId: Long, isArchived: Boolean, updatedAt: Instant)

// 3. 调用处直接传入 Instant
noteDao.updateArchiveStatus(noteId, true, Instant.now())
```

**关键教训**:
- Room 的 `@TypeConverters` 已配置 `Instant ↔ Long` 转换，但 **DAO 方法签名必须明确类型**
- 不要在调用处手动转换类型（`.toEpochMilli()`），让 Room 自动处理
- **KSP 缓存会掩盖类型错误**，遇到 `Storage already registered` 必须清理缓存（`./gradlew clean` 或删除 `.gradle/` 和 `app/build/`）

**为什么会踩两次**:
第一次修改只改了一个方法，第二次又复制了错误模式到另一个方法。应该在第一次修复时就全局搜索 `updatePinStatus|updateArchiveStatus` 检查所有调用处。

### 坑 #2: UI 层漏接线 - 功能实现了但没人调用

**现象**:
- Repository 层已实现 `removeTagFromAllNotes()` 和 `deleteTagAndMoveNotesToTrash()`
- HomeViewModel 也暴露了对应方法
- 但 DrawerContent 的菜单点击仍然弹 Toast "功能即将上线"

**根本原因**:
从 Repository → ViewModel → UI 的数据流有三层，必须**每一层都接线**：
1. ✅ Repository 实现了方法
2. ✅ HomeViewModel 调用了 Repository
3. ❌ **DrawerContent 没有接收回调参数**
4. ❌ **HomeScreen 没有传递 ViewModel 方法给 DrawerContent**

**正确的接线流程**:
```kotlin
// 1. DrawerContent 新增回调参数
fun DrawerContent(
    onRemoveTag: (String) -> Unit = {},
    onDeleteTagAndNotes: (Long) -> Unit = {}
)

// 2. DrawerTagItem 传递回调
DrawerTagItem(
    onRemoveTag = { onRemoveTag(tag.name) },
    onDeleteTagAndNotes = { onDeleteTagAndNotes(tag.id) }
)

// 3. DropdownMenu 调用回调
onClick = {
    menuExpanded = false
    onRemoveTag()  // 不再是 Toast！
}

// 4. HomeScreen 连接 ViewModel
DrawerContent(
    onRemoveTag = { tagName ->
        homeViewModel.removeTagFromAllNotes(tagName)
    }
)
```

**关键教训**:
- Compose 的回调传递是**显式的**，不像 LiveData 那样自动订阅
- 每增加一个新功能，必须检查完整的调用链：Repository → ViewModel → Screen → Component
- 不要留 TODO 注释，要么不写代码，要么一次性写完整

### 坑 #3: TopAppBar 出现冗余图标 - 多个入口造成混乱

**现象**:
- 主页右上角出现一个垃圾桶图标（`Icons.Default.Delete`）
- 侧边栏底部也有"🗑️ 回收站"入口
- 用户不知道该点哪个

**根本原因**:
在 Stage 10 创建 ArchiveScreen 时，为了快速测试导航，在 `HomeScreen.kt` 的 `TopAppBar.actions` 里临时添加了一个回收站按钮。后来 Stage 11 重构 DrawerContent 时，又在底部添加了正式的回收站入口，但忘记删除临时按钮。

**正确的 UI 设计**:
- **主页 TopAppBar**: 只保留核心操作（菜单、搜索），不应有二级功能入口
- **侧边栏底部**: 系统级入口（回收站、帮助中心）的统一位置
- **原则**: 一个功能只有一个主要入口，避免用户困惑

**关键教训**:
- 临时测试代码必须在 commit 前清理
- UI 重构时要检查是否有旧代码残留
- 参考 Flomo 原版设计：主页极简，系统功能在抽屉底部

## 📝 数据库设计决策

### 为什么 Tag 模型没有 icon 字段？

**当前状态**:
- `TagEntity` 只有 `id`, `name`, `createdAt`, `usageCount` 四个字段
- `TagEditScreen` 可以选择 emoji，但 `onSave` 的 `newIcon` 参数无处存储

**原因**:
1. Stage 12 的原始需求没有明确要求持久化 emoji 图标
2. 添加新字段需要数据库迁移（`Migration(2, 3)`），超出当前 Stage 范围
3. MVP 阶段优先实现核心功能（标签过滤、正则替换），图标是视觉增强

**后续计划（Stage 13 或更晚）**:
```kotlin
// 未来的 TagEntity
@Entity(tableName = "tags")
data class TagEntity(
    val id: Long,
    val name: String,
    val icon: String?,  // 新增字段：emoji 字符或 null
    val createdAt: Instant,
    val usageCount: Int
)

// 数据库迁移
val MIGRATION_2_3 = object : Migration(2, 3) {
    override fun migrate(database: SupportSQLiteDatabase) {
        database.execSQL("ALTER TABLE tags ADD COLUMN icon TEXT")
    }
}
```

**关键教训**:
- 数据库模型修改必须提前规划，不能随意添加字段
- UI 可以先行开发（TagEditScreen），等数据层准备好再连接
- MVP 开发要控制范围，不要在一个 Stage 里做太多事

## 🔒 安全相关

### 正则表达式边界匹配的重要性

**问题场景**:
用户有两个标签 `#task` 和 `#task_list`，如果执行"仅移除标签 #task"，错误的正则会把 `#task_list` 也破坏掉。

**错误的实现**:
```kotlin
// ❌ 简单替换（危险！）
content.replace("#$tagName", "")
// "今天的 #task 和 #task_list" → "今天的  和 _list"  // task_list 被破坏！
```

**正确的实现**:
```kotlin
// ✅ 使用边界匹配
val pattern = Regex("""(?<=\s|^)#${Regex.escape(tagName)}(?=\s|$)""")
content.replace(pattern, "")
// "今天的 #task 和 #task_list" → "今天的  和 #task_list"  // task_list 保留！
```

**边界模式解释**:
- `(?<=\s|^)`: 向后查找，确保标签前是空格或字符串开头
- `#${Regex.escape(tagName)}`: 标签本身，转义特殊字符防止注入
- `(?=\s|$)`: 向前查找，确保标签后是空格或字符串结尾

**测试用例**:
```kotlin
// 应该匹配的
"#task"          → 匹配
" #task "        → 匹配
"今天的 #task。"  → 匹配

// 不应该匹配的
"#task_list"     → 不匹配（后面是 _）
"#tasks"         → 不匹配（后面是 s）
"email@task.com" → 不匹配（前面是 @）
```

**关键教训**:
- 涉及用户数据的正则替换必须使用边界匹配
- 所有正则模式必须写单元测试（本项目尚未添加，应在 Stage 13 补充）
- `Regex.escape()` 防止用户输入的特殊字符（如 `#c++`）破坏正则

## 📖 经验总结

### 开发流程改进
1. **类型修改要全局搜索**: 修改方法签名时，必须用 Grep 找出所有调用处
2. **UI 功能分层检查**: Repository → ViewModel → Screen → Component 每一层都要验证
3. **测试代码及时清理**: 临时测试按钮要在 commit 前删除
4. **KSP 错误要清缓存**: 遇到 `Storage already registered` 先 `./gradlew clean`

### Git Commit 最佳实践
- ✅ 使用 HEREDOC 写多行 commit message（防止引号转义问题）
- ✅ 按类别分段：Features / Bug Fixes / Files Modified / Known Limitations
- ✅ 记录关键修复原因（如"为什么改成 Instant"）
- ✅ 列出已知限制（如"icon 字段未实现"），避免后续重复排查

### 下次应该做的更好
- [ ] 在修改 DAO 签名时立即添加单元测试
- [ ] UI 组件的回调参数应该在设计阶段就规划好
- [ ] 数据库迁移应该提前评估，不要临时添加字段
- [ ] 正则替换功能必须写自动化测试（Instrumented Test）
