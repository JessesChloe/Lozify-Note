### 1. 修复图片 OOM 崩溃（OutOfMemoryError）

**问题描述：**
- 用户添加高分辨率照片（12MP+）后点击保存，应用直接闪退
- 闪退后应用再也无法打开，持续崩溃循环

**根因分析：**
- `ImageUtils.copyImageToPrivateStorage()` 直接使用 `BitmapFactory.decodeStream()` 加载完整图片
- 现代手机相机照片（4000x3000 像素）在 ARGB_8888 格式下需要 ~46MB 内存
- Android 应用默认堆内存上限：64-256MB
- 加载 2-3 张高分辨率照片直接触发 `OutOfMemoryError`

**修复方案：**
- **两步加载策略**：
  1. 第一步：`BitmapFactory.Options.inJustDecodeBounds = true` 只读取尺寸，不分配内存
  2. 第二步：计算 `inSampleSize` 采样率，缩小加载
- **新增 `calculateInSampleSize()` 辅助方法**：
  - 计算最大的 2 的幂次采样率
  - 例如：4000x3000 图片，采样率 2 → 实际加载 2000x1500
- **内存占用对比**：
  - 修复前：12MP 图片 → 46MB
  - 修复后：12MP 图片 → 11MB（节省 76%）
- **异常防护**：
  - 添加 `catch (e: OutOfMemoryError)` 捕获
  - 严格在 `finally` 块中调用 `bitmap.recycle()` 释放内存

**修改文件：**
- `core/common/ImageUtils.kt` - 重构 `copyImageToPrivateStorage()` 方法，新增 `calculateInSampleSize()` 辅助方法

### 2. 修复嵌套滚动布局崩溃（IllegalStateException）

**问题描述：**
- 用户抓取 Logcat 日志，发现真正的崩溃错误：
  ```
  java.lang.IllegalStateException: Vertically scrollable component was measured 
  with an infinity maximum height constraints, which is disallowed.
  ```
- 崩溃指向：`androidx.compose.foundation.lazy.grid.LazyGridKt`

**根因分析：**
- `NoteCard.kt` 中使用了 `LazyVerticalGrid`（可滚动组件）渲染图片网格
- `NoteCard` 作为 item 嵌套在 `HomeScreen.kt` 的 `LazyColumn`（主列表）中
- Compose 禁止在无限高度约束下测量可滚动组件
- `LazyColumn` 给子项传递 `maxHeight = Infinity` 约束
- `LazyVerticalGrid` 无法在无限高度下计算虚拟化窗口 → 抛出 `IllegalStateException`

**修复方案：**
- **彻底移除 `LazyVerticalGrid`**，改用非滚动的 `Column` + `Row` 组合
- **布局策略**：
  - 使用 `attachments.chunked(3)` 将附件列表按每行 3 个分组
  - 每行用 `Row` 布局，每个图片用 `Modifier.weight(1f)` 平分宽度
  - 最后一行不足 3 个元素时，用 `Spacer(Modifier.weight(1f))` 填充空槽保持对齐
- **效果**：
  - 图片网格随 `LazyColumn` 主列表自然滚动
  - 无需内部滚动，布局测量可预测
  - 性能更优（避免双重虚拟化开销）

**修改文件：**
- `presentation/home/NoteCard.kt` - 替换图片网格实现，移除 `LazyVerticalGrid` 相关导入

## 技术决策记录

### ADR-007: 采样加载（inSampleSize）防止 OOM

**背景：**
- Android Bitmap 内存分配在 Native Heap，不受 JVM GC 自动管理
- 现代手机相机照片分辨率极高（12MP+），直接加载极易 OOM
- 笔记应用需要支持用户从相册选择任意照片

**决策：**
- 采用 `BitmapFactory.Options.inSampleSize` 两步加载策略
- 第一步只读尺寸（`inJustDecodeBounds = true`）
- 第二步按采样率加载（`inSampleSize = 2/4/8...`）
- 最大尺寸限制：2048x2048 像素（`MAX_IMAGE_DIMENSION`）
- JPEG 压缩质量：85%（`JPEG_QUALITY`）

**替代方案（已拒绝）：**
1. 限制用户只能选择小于 5MB 的图片 → 用户体验差
2. 使用第三方压缩库（如 Luban）→ 增加依赖复杂度
3. 在后台线程异步加载 → 仍然会 OOM，只是延迟崩溃

**后果：**
- ✅ 内存占用降低 70-80%
- ✅ 支持任意分辨率照片
- ⚠️ 超高分辨率图片会损失部分细节（可接受，因为卡片显示尺寸有限）

---

### ADR-008: 非滚动布局避免嵌套滚动冲突

**背景：**
- Jetpack Compose 的 `LazyColumn`/`LazyRow`/`LazyGrid` 是虚拟化可滚动组件
- 嵌套滚动组件会导致测量约束冲突
- Compose 抛出 `IllegalStateException` 防止无限递归测量

**决策：**
- `NoteCard` 作为 `LazyColumn` 的 item，必须使用非滚动布局
- 图片网格使用 `Column` + `Row` 组合，而非 `LazyVerticalGrid`
- 通过 `chunked(3)` + `Spacer` 实现等宽 3 列布局

**替代方案（已拒绝）：**
1. 给 `LazyVerticalGrid` 指定固定高度（`.height(300.dp)`）→ 会截断超过高度的图片
2. 使用 `FlowRow`（实验性 API）→ 需要额外依赖且 API 不稳定
3. 自定义 `Layout` Composable → 过度工程化

**后果：**
- ✅ 布局测量可预测，无崩溃风险
- ✅ 性能更优（避免双重虚拟化）
- ✅ 代码更简单（使用原生 Column/Row）
- ⚠️ 图片数量极多时（100+ 张）会影响性能（MVP 阶段可接受）

## 学习与反思

### 1. Compose 布局测量约束系统

**关键知识点：**
- `LazyColumn`/`LazyGrid` 等虚拟化组件需要确定的最大高度才能计算视口
- 父容器对子项传递的约束包括 `minWidth/maxWidth/minHeight/maxHeight`
- 当 `maxHeight = Infinity` 时，嵌套的可滚动组件无法测量 → 崩溃
- 解决方案：使用非滚动布局（`Column`/`Row`）或给可滚动组件指定固定高度

**经验教训：**
- ❌ 不要在 `LazyColumn` 的 item 中使用 `LazyGrid`/`LazyRow`
- ✅ 使用 `Column` + `Row` 或 `FlowRow`（实验性）代替
- ✅ 如必须使用 `LazyGrid`，需指定 `.height()` 固定高度

---

### 2. Android Bitmap 内存管理

**关键知识点：**
- Bitmap 内存分配在 Native Heap，不受 JVM GC 管理
- 必须显式调用 `bitmap.recycle()` 释放内存
- `inSampleSize` 必须是 2 的幂次（1, 2, 4, 8, 16...）
- 采样加载在解码阶段就减少内存分配，而非先分配后缩放

**内存占用计算公式：**
```
内存占用 = 宽度 × 高度 × 每像素字节数

ARGB_8888: 每像素 4 字节
RGB_565: 每像素 2 字节（颜色精度降低）

示例：4000x3000 像素照片
ARGB_8888: 4000 × 3000 × 4 = 48,000,000 字节 ≈ 46MB
inSampleSize=2: 2000 × 1500 × 4 = 12,000,000 字节 ≈ 11MB
```

**经验教训：**
- ❌ 不要直接 `BitmapFactory.decodeStream()` 加载相机照片
- ✅ 先读尺寸（`inJustDecodeBounds = true`），再计算采样率
- ✅ 在 `finally` 块中严格调用 `recycle()`

---

### 3. 异常容错的防御式编程

**关键知识点：**
- 单个操作失败不应导致整个流程崩溃
- 对于批量操作（如处理多张图片），应逐个捕获异常
- 数据库事务要么全部成功，要么全部回滚，避免"半成品"记录

**本次实践：**
- ✅ `AttachmentRepositoryImpl` 在最外层捕获所有异常，返回 `null`
- ✅ `EditorViewModel` 对每张图片处理单独 `try-catch`
- ✅ 允许部分成功：3 张图片中有 1 张失败，其他 2 张仍然保存

**经验教训：**
- ❌ 不要让一个图片处理失败导致整个笔记保存失败
- ✅ 优雅降级：部分成功优于全部失败
- ✅ 记录异常日志（`e.printStackTrace()`）便于调试

### 学习与反思

#### **1. 正则表达式跨行匹配陷阱**

**关键知识点：**
- Kotlin/Java 正则默认是单行模式（`.` 不匹配 `\n`）
- 启用 DOTALL 模式的两种方式：
  1. 内联标志：`(?s)` 前缀
  2. Pattern Flag：`Pattern.DOTALL` (Java) 或 `RegexOption.DOT_MATCHES_ALL` (Kotlin)
- Kotlin Regex 构造函数支持 `Set<RegexOption>` 参数

**经验教训：**
- ❌ 不要假设正则默认支持跨行匹配
- ✅ 对于可能跨行的内容，始终使用 `(?s)` 或 `DOT_MATCHES_ALL`
- ✅ 单元测试必须包含多行文本场景

---

#### **2. Compose TextFieldValue 选区语义**

**关键知识点：**
- `TextRange.start` 和 `end` 不保证 `start ≤ end`
- 反向选择时：`start > end` 是正常状态
- `TextRange.min` 和 `max` 扩展属性自动处理顺序

**API 对比：**
```kotlin
val selection = TextRange(start = 10, end = 5)  // 反向选择

selection.start  // 10
selection.end    // 5
selection.min    // 5  ✅ 自动取最小值
selection.max    // 10 ✅ 自动取最大值
```

**经验教训：**
- ❌ 不要用 `if (start > end)` 拦截
- ❌ 不要手动交换 start/end
- ✅ 始终使用 `min/max` 扩展属性

---

#### **3. 防御式编程的边界**

**关键知识点：**
- 过度验证会拦截合法输入
- `coerceIn()` 会改变值的语义
- 边界检查应该只验证"越界"，不应该"修正"输入

**本次踩坑：**
```kotlin
// ❌ 过度验证（改变语义）
val safeStart = selection.start.coerceIn(0, text.length)
val safeEnd = selection.end.coerceIn(0, text.length)

// ✅ 纯验证（保留语义）
val min = selection.min
val max = selection.max
if (min < 0 || max > text.length) return
```

**经验教训：**
- ❌ 不要用 `coerceIn()` "修正"用户输入
- ✅ 验证边界后直接拒绝或使用原始值
- ✅ 让 API 自带的语义处理逻辑生效（如 `min/max`）

### **坑 #3: 正则表达式默认不匹配换行符**

**踩坑过程：**
1. 实现富文本解析：`Regex("""\*\*(.+?)\*\*""")`
2. 单行文本测试：完美工作
3. 用户测试跨行格式：完全失效
4. 困惑：正则没问题啊，为什么跨行就不行了？
5. 调试发现：`**第一行\n第二行**` 这段文本，正则匹配失败
6. 查文档才知道：`.` 默认不匹配 `\n`

**根本原因：**
- Kotlin/Java 正则表达式默认是**单行模式**
- `.` 元字符匹配"除换行符外的任意字符"
- 必须显式启用 DOTALL 模式（让 `.` 匹配包括换行符在内的任意字符）

**首次尝试修复（走弯路）：**
- 想用 `[\s\S]+?` 替代 `.+?`
- 理由：`\s` 匹配空白字符（包括 `\n`），`\S` 匹配非空白，组合起来 = 任意字符
- 问题：可读性差，其他开发者看不懂

**最终修复：**
```kotlin
// ❌ 错误：单行模式（默认）
Regex("""\*\*(.+?)\*\*""")

// ✅ 正确：启用 DOTALL 模式
Regex("""\*\*(?s)(.+?)\*\*""")  // (?s) 内联标志
```

**扩展知识：启用 DOTALL 的三种方式**
```kotlin
// 方式 1: 内联标志（推荐，简洁）
Regex("""(?s)\*\*(.+?)\*\*""")

// 方式 2: RegexOption（Kotlin 风格）
Regex("""\*\*(.+?)\*\*""", RegexOption.DOT_MATCHES_ALL)

// 方式 3: Pattern Flag（Java 互操作）
Pattern.compile("""\*\*(.+?)\*\*""", Pattern.DOTALL)
```

**影响范围：**
- 不仅仅是解析方法，`stripFormatting()` 和 `countFormatting()` 也需要修复
- 必须全局统一：所有处理富文本的正则都加 `(?s)`

**避坑指南：**
```kotlin
// ❌ 错误：假设正则默认支持跨行
val boldPattern = Regex("""\*\*(.+?)\*\*""")
boldPattern.find("**第一行\n第二行**")  // null（匹配失败）

// ✅ 正确：明确启用 DOTALL
val boldPattern = Regex("""\*\*(?s)(.+?)\*\*""")
boldPattern.find("**第一行\n第二行**")  // 成功匹配

// 📝 单元测试必须包含换行符场景
@Test
fun testMultilineFormatting() {
    val content = "**第一行\n第二行**"
    val result = RichTextUtils.buildAnnotatedStringWithFormatting(content)
    // 验证跨行内容被正确加粗
}
```

**记住的教训：**
- ⚠️ `.` 不等于"任意字符"，它排除了换行符
- ⚠️ 不要用单行测试验证跨行功能
- ⚠️ 修复一个地方后，搜索所有相同模式的正则一并修复
- ✅ 对于可能跨行的内容，始终使用 `(?s)` 标志
- ✅ 单元测试必须覆盖多行场景

### **坑 #4: Kotlin 扩展函数全限定名调用错误**

**踩坑过程：**
1. 需要从 `Flow<Note?>` 中获取第一个值
2. 想到 Kotlin 有 `firstOrNull()` 扩展函数

   ```kotlin
   val note = noteRepository.getNoteById(noteId)
   kotlinx.coroutines.flow.firstOrNull(note)?.let { ... }
   ```
4. 编译失败：`Unresolved reference 'firstOrNull'`
5. 困惑：明明写了完整的包名，为什么找不到？

**根本原因：**
- Kotlin 扩展函数是**接收者函数**，不是普通的静态方法
- 不能用 `包名.函数名(接收者)` 的 Java 静态方法风格调用
- 必须用 `接收者.函数名()` 的链式调用风格

**错误理解：**
```kotlin
// ❌ 错误：把扩展函数当成静态方法
kotlinx.coroutines.flow.firstOrNull(note)
// 相当于试图调用：
// package kotlinx.coroutines.flow {
//     fun firstOrNull(flow: Flow<T>): T?  // 不存在这样的函数！
// }
```

**正确理解：**
```kotlin
// ✅ 正确：扩展函数的本质
// 定义：
fun <T> Flow<T>.firstOrNull(): T? { ... }

// 调用方式 1：接收者调用（推荐）
note.firstOrNull()

// 调用方式 2：导入后使用
import kotlinx.coroutines.flow.firstOrNull
note.firstOrNull()

// ❌ 错误：全限定名包裹参数
kotlinx.coroutines.flow.firstOrNull(note)  // 语法错误
```

**修复步骤：**
1. 添加 import：`import kotlinx.coroutines.flow.firstOrNull`
2. 使用链式调用：`noteFlow.firstOrNull()`

**避坑指南：**
```kotlin
// ❌ 错误模式：试图用包名调用扩展函数
kotlin.text.substring(text, 0, 5)           // ❌
kotlin.collections.map(list) { it * 2 }    // ❌
kotlinx.coroutines.flow.collect(flow) {}   // ❌

// ✅ 正确模式：接收者链式调用
text.substring(0, 5)                        // ✅
list.map { it * 2 }                         // ✅
flow.collect {}                             // ✅

// 📝 判断是否为扩展函数：
// 1. 函数定义有接收者类型（fun Type.method()）
// 2. 调用时对象在前，函数在后（object.method()）
```

**记住的教训：**
- ⚠️ 扩展函数 ≠ 静态方法，不能用包名包裹参数调用
- ⚠️ 全限定名调用只适用于普通函数和静态方法
- ⚠️ 遇到 `Unresolved reference` 先检查是否为扩展函数
- ✅ 扩展函数必须用 `receiver.function()` 风格调用
- ✅ 优先 import 后使用，而非试图全限定名调用

### **坑 #5: DAO 方法定义遗漏**

**踩坑过程：**
1. 在 `NoteRepositoryImpl` 中编写级联删除逻辑
2. 调用 `relationDao.deleteAllIncomingRelations(noteId)`
3. IDE 无报错，代码提示正常
4. 编译失败：`Unresolved reference 'deleteAllIncomingRelations'`
5. 检查 DAO 接口：只定义了 `deleteAllOutgoingRelations()`，没有 Incoming 版本
6. 原因：复制粘贴时只写了一半，忘记写对称方法

**根本原因：**
- 笔记关系是双向的（A @mentions B，需要清理两个方向）
- `from_note_id` 方向有删除方法，`to_note_id` 方向遗漏了
- 调用不存在的方法导致编译失败

**IDE 为什么没提前报错？**
- 在 `NoteRepositoryImpl.kt` 中编写时，IDE 尚未完全解析 DAO 接口
- Room 的 DAO 是编译期生成实现类，开发时接口是"空壳"
- 只有 Gradle 编译时 KSP 才会检查方法签名

**修复：**
```kotlin
// ✅ 补充缺失的 DAO 方法
@Query("DELETE FROM note_relations WHERE to_note_id = :noteId")
suspend fun deleteAllIncomingRelations(noteId: Long)
```

**避坑指南：**
```kotlin
// ❌ 错误模式：假设对称操作自动存在
relationDao.deleteAllOutgoingRelations(noteId)  // ✅ 已定义
relationDao.deleteAllIncomingRelations(noteId)  // ❌ 未定义

// ✅ 正确模式：编写对称操作时同步定义
interface NoteRelationDao {
    // 删除出链（A → B，删除 A 的记录）
    @Query("DELETE FROM note_relations WHERE from_note_id = :noteId")
    suspend fun deleteAllOutgoingRelations(noteId: Long)
    
    // 删除入链（A → B，删除 B 的记录）
    @Query("DELETE FROM note_relations WHERE to_note_id = :noteId")
    suspend fun deleteAllIncomingRelations(noteId: Long)
}

// 📝 检查清单：
// 1. 双向关系表必须有双向删除方法
// 2. 多对多关系表必须有两个实体的删除方法
// 3. 级联删除必须覆盖所有外键方向
```

**记住的教训：**
- ⚠️ 双向关系必须有对称的操作方法
- ⚠️ IDE 不报错 ≠ 方法已定义（Room DAO 是编译期生成）
- ⚠️ 级联删除不能只依赖 `ForeignKey.CASCADE`，需要显式清理
- ✅ 定义删除方法时，立即检查是否有对称方向
- ✅ 编译失败时，先检查 DAO 接口方法定义

### **坑 #6: 交互式组件渲染策略错误**

**踩坑过程：**
1. 需求：`- [ ]` 生成可点击的待办复选框
2. 第一版实现：用 Unicode 符号 `☐`/`☑` 渲染
3. 用户点击：没有任何反应
4. 原因：`ClickableText` 只能处理文本点击，不能处理复选框状态切换
5. 意识到：需要真实的 `Checkbox` 组件

**根本原因：**
- 富文本渲染用的是 `AnnotatedString` + `ClickableText`
- `ClickableText` 只支持点击事件，不支持状态管理（如勾选/取消勾选）
- 复选框需要 Material3 的 `Checkbox` 组件 + 状态绑定

**修复策略：内容分离 + 组件混合渲染**
```kotlin
// 步骤 1: 解析内容，分离复选框行和普通文本行
val contentLines = content.split("\n")
val checkboxItems = contentLines.mapIndexedNotNull { index, line ->
    val match = Regex("""^- \[([ x])\] (.+)$""").find(line)
    match?.let {
        CheckboxItem(
            lineIndex = index,
            isChecked = it.groupValues[1] == "x",
            text = it.groupValues[2]
        )
    }
}
val nonCheckboxContent = contentLines.filterIndexed { index, line ->
    !line.matches(Regex("""^- \[([ x])\] .+$"""))
}.joinToString("\n")

// 步骤 2: 分别渲染
Column {
    // 真实 Checkbox 组件（可交互）
    checkboxItems.forEach { item ->
        Row {
            Checkbox(
                checked = item.isChecked,
                onCheckedChange = { isChecked ->
                    // 更新数据库
                    onCheckboxToggle(noteId, newContent)
                }
            )
            Text(item.text)
        }
    }
    
    // 富文本内容（只读）
    ClickableText(text = annotatedContent, ...)
}
```

**避坑指南：**
```kotlin
// ❌ 错误模式：把状态组件当成文本渲染
val annotatedString = buildAnnotatedString {
    append("☐ 待办事项")  // Unicode 符号，无法交互
}
ClickableText(text = annotatedString) {
    // ❌ 点击文本无法切换复选框状态
}

// ✅ 正确模式：分离内容，混合渲染
Column {
    // 状态组件用真实 Composable
    Checkbox(checked = isChecked, onCheckedChange = { ... })
    
    // 只读文本用 AnnotatedString
    ClickableText(text = richText, ...)
}

// 📝 判断标准：
// 需要状态管理（勾选、输入、滑动）→ 真实 Composable
// 只需要显示样式（颜色、加粗、点击）→ AnnotatedString
```

**记住的教训：**
- ⚠️ `AnnotatedString` 只能处理样式，不能处理状态
- ⚠️ Unicode 符号看起来像组件，但无法交互
- ⚠️ 复杂富文本需要"内容分离 + 混合渲染"策略
- ✅ 状态组件用真实 Composable（Checkbox, TextField, Button）
- ✅ 样式文本用 AnnotatedString（加粗、颜色、点击跳转）

### **坑 #7: 数据库级联删除不触发**

**踩坑过程：**
1. 配置了 `ForeignKey.CASCADE` 约束
2. 删除笔记后，期望关联数据自动删除
3. 实际测试：标签关联、附件、关系都没有被删除
4. 困惑：CASCADE 不是应该自动级联吗？

**根本原因：**
- Room 的 `@ForeignKey` CASCADE 依赖 SQLite 的外键约束
- SQLite 的外键约束默认**未启用**
- 必须在数据库打开时执行 `PRAGMA foreign_keys = ON`
- 即使启用了，CASCADE 的触发时机依赖事务边界，不一定立即生效

**为什么不能只依赖 CASCADE：**
1. **触发时机不确定**：依赖数据库引擎事务提交
2. **调试困难**：CASCADE 失败不会抛出异常，数据静默残留
3. **跨数据库兼容性**：不同数据库的 CASCADE 行为不一致

**最终方案：双重保险（显式删除 + CASCADE）**
```kotlin
override suspend fun hardDeleteNote(noteId: Long) {
    val noteEntity = noteDao.getNoteById(noteId).first()
    
    noteEntity?.let { entity ->
        // 显式删除所有关联（第一重保险）
        tagDao.deleteAllTagsForNote(noteId)
        attachmentDao.deleteAllAttachmentsForNote(noteId)
        relationDao.deleteAllOutgoingRelations(noteId)
        relationDao.deleteAllIncomingRelations(noteId)
        
        // 删除笔记（第二重保险：CASCADE）
        noteDao.deleteNote(entity)
    }
}
```

**避坑指南：**
```kotlin
// ❌ 错误模式：完全依赖 CASCADE
@Entity(
    foreignKeys = [ForeignKey(
        entity = NoteEntity::class,
        parentColumns = ["id"],
        childColumns = ["note_id"],
        onDelete = ForeignKey.CASCADE  // ⚠️ 不一定可靠
    )]
)
data class AttachmentEntity(...)

// 然后在删除时：
noteDao.deleteNote(entity)  // ❌ 假设 CASCADE 会自动清理

// ✅ 正确模式：显式删除 + CASCADE 双重保险
fun hardDeleteNote(noteId: Long) {
    // 显式清理（立即生效，可控）
    attachmentDao.deleteAllAttachmentsForNote(noteId)
    tagDao.deleteAllTagsForNote(noteId)
    
    // 删除主实体（CASCADE 作为兜底）
    noteDao.deleteNote(entity)
}

// 📝 配置外键启用（DatabaseModule）
Room.databaseBuilder(...)
    .addCallback(object : RoomDatabase.Callback() {
        override fun onCreate(db: SupportSQLiteDatabase) {
            super.onCreate(db)
            db.execSQL("PRAGMA foreign_keys = ON")
        }
        override fun onOpen(db: SupportSQLiteDatabase) {
            super.onOpen(db)
            db.execSQL("PRAGMA foreign_keys = ON")
        }
    })
```

**记住的教训：**
- ⚠️ `ForeignKey.CASCADE` 不等于"一定会级联"
- ⚠️ SQLite 外键约束默认关闭，必须显式启用
- ⚠️ CASCADE 失败不报错，数据会静默残留
- ✅ 采用"显式删除 + CASCADE 兜底"的双重保险策略
- ✅ 在数据库打开回调中启用 `PRAGMA foreign_keys = ON`
